## 实际发现并修复的阻断

首次实况 run `20261025T013301558105+0000-e55cd7cb` 成功补采 176 个 POI，但 L3 连续报告选中网格的 A/B 门店不足，最终 `backtrack_limit`。没有把失败录制成成功。

原因：L2 总是填满最多 4 个选区，L3 却对全部候选统一分级；排名加分使后面的网格可能全部为 C。取消后补选下一名仍可能重复失败。

修复：L2 在现有上限内，使用同一套 L3 数学提前检查，选择满足每区 A/B 门店要求的最长排名前缀。评分权重、分级比例、最低门店数和回退上限均未降低。若所有前缀都不可行，继续保留原有失败与回退路径。此选择是按排名收缩范围，不声称求得全局最优选区。

## 交付物与业务边界

验证：Agent/录制定向测试 7 项通过；全量 `uv run pytest -q` 初跑 263 项通过、3 项失败。失败分别为演示导出增加临时第六场景、旧测试要求发生已被预检避免的回退，以及压缩包新增 bread-trial 后目录测试仍只列两个产品。交付分支保留原五份页面样例，更新后两项预期；相关目录、选区与回退测试共 7 项复验通过。未声称重新完整跑过全量测试。实况与录制回放均独立执行成功。

- `discovery.json` / `agent/steps.jsonl`：Agent 搜索过程与渠道补齐结果。
- `zones.json` / `terminals.json`：选区、门店分级及理由。
- `materials.json` / `pack.json`：话术、拜访安排与来源证据。
- `ledger.jsonl` / `status.json`：逐关检查、失败与最终状态。
- 上述完整文件由每次运行在 `runs/<run-id>/` 生成；公开录制包含真实模型回复及去除联系方式后的高德基础响应，可重新生成这些交付物。

这次验证证明了缺渠道数据时自主补采并生成首批拓客执行包的闭环。只有 L1D 使用模型，其余关卡标记为 rules；单网格 7 家 A/B 首访对象不是四周铺市量的证明。POI 类别不证明进货意愿，办公/健身话术仍有通用零售措辞，现场使用前需按渠道调整。实际成交与商业收益尚未验证。
